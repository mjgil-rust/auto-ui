Reviewed the uploaded Repomix snapshot. Overall: **good direction, but not production-ready yet**. The repo has a useful workspace split, concrete `rust-chatbot` and GPUI flows, report writing, scenario examples, and a clear desktop-coexistence philosophy. The implementation, however, overstates its maturity: several “generic harness” pieces are scaffolded or bypassed, CI is likely brittle, and a few bugs can cause false reports, trace misses, or hung processes. 

## Verdict

**Assessment: B- as an internal prototype, C+ as a reusable automation framework.**

The strongest part is the **target-specific adapter work**: `rust-chatbot` and GPUI both have plausible end-to-end scenario runners, and the repo has a clean Cargo workspace, examples, docs, and a report model. The weakest part is the gap between the advertised generic architecture and what is actually wired together. The `TargetAdapter`, `AdapterRegistry`, lifecycle orchestration, `WindowDriver` abstraction, and interactive orchestrator are mostly not used by the real adapters; the adapters call X11/process helpers directly.

## What is solid

The workspace split is sensible: CLI, core, artifacts, X11 driver, rust-chatbot adapter, and GPUI adapter are separated. That is the right macro-architecture for a reusable desktop harness.

The repo also has a reasonably good scenario surface. `run --config`, convenience commands, TOML examples, validation commands, report schema output, and an inspection command are all represented. The docs make the intended operational model clear: startup-driven automation is preferred, foreground control is opt-in, and target app builds are intentionally out-of-band.

The GPUI adapter is a good addition because it validates the design beyond one app: it uses startup-driven runs with app-generated artifacts rather than only pointer/window automation. The examples also make the intended user workflows easy to understand.

## High-priority issues

### 1. The generic architecture is partly scaffold, not integrated

The design says the core owns adapter lifecycle, orchestration, event aggregation, and pluggable window behavior, but the real adapters do not implement `TargetAdapter`; search shows `TargetAdapter` impls only in core tests, not in `auto-ui-adapter-rust-chatbot` or `auto-ui-adapter-gpui`. Similarly, the `WindowDriver` trait has a fake implementation but no real X11 implementation wired through it.

The clearest example is `InteractiveWindowOrchestrator`: it returns hardcoded geometry, logs events, and leaves resize/screenshot/restore as “in a full implementation” no-ops. It does not call the X11 driver at all. 

**Impact:** Consumers will assume the core abstractions are production harness logic, but the production behavior is still embedded in adapter-specific code. This makes future targets harder to add than the design suggests.

**Fix:** Pick one path. Either remove/de-emphasize the generic abstractions until they are used, or migrate both adapters to implement `TargetAdapter` and route window operations through a real `WindowDriver` implementation.

### 2. CI will likely fail or be flaky because non-ignored tests require Xvfb/openbox

The CI installs Rust and runs `cargo test --workspace`, but the workflow does not install Xvfb/openbox/ImageMagick/X11 tools. Meanwhile, `display.rs` contains multiple non-ignored tests that call `HeadlessDisplay::start("800x600x24")`, including tests for killing Xvfb/openbox and checking display numbers. Some comments even label these as “FAILING TESTS.” 

**Impact:** On a normal GitHub Ubuntu runner, these tests are very likely to fail unless the tools happen to exist. They also mutate global `DISPLAY`, which is unsafe under `--test-threads=4`.

**Fix:** Install Xvfb, openbox, and ImageMagick in CI. Mark tests that require a visible display as `#[ignore]` only as a fallback when CI cannot provide one. Run display-dependent tests serially or in a dedicated job that has system dependencies installed.

### 3. The report JSON schema rejects the reports the code now emits

`ArtifactRef` includes a `source` field, and tests expect serialized artifacts to include `"source": "generated"`. But `report_schema_json()` defines `artifact_ref` with `additionalProperties: false` and only lists `kind`, `path`, `description`, and `metadata`; it omits `source`. That means actual current reports containing `source` are invalid under the exported schema. 

**Impact:** Any downstream consumer using `auto-ui report-schema` to validate reports can reject valid reports generated by the tool.

**Fix:** Add `source` to the schema properties with enum `["generated", "imported"]`; decide whether it is optional or required. Add a real JSON-schema validation test for a report produced by `Report::new().add_artifact()`.

**Status: FIXED** — `source` field added to schema with enum `["generated", "imported"]`. Added `artifact_ref_schema_includes_source_field` regression test. Also fixed missing `#[test]` on `error_report_conforms_to_schema` function.

### 4. Failure reports are written as `running`, not `error`

Several adapters write a report on failure, but they do not call `report.finish_error(...)` before `write_report(...)`. In `rust-chatbot` debug and all three GPUI scenarios, the failure path simply writes the partially initialized report. 

**Impact:** A failed run can leave `report.json` with `status: "running"` and no error message, which is misleading and breaks report consumers.

**Fix:** In every `if result.is_err()` block, call `report.finish_error(format!("{:#}", result.as_ref().unwrap_err()))` before writing. Then test this for each scenario path.

**Status: FIXED** — All 6 error paths (rust-chatbot: debug, header_debug, prompt_debug; GPUI: scroll_matrix, scrollbar_trace, conversation_paint) now call `report.finish_error()` before `write_report()`.

### 5. `rust-chatbot` trace matching likely misses quoted `session_id`s

The trace parser supports quoted values, and tests include quoted `session_id="..."` cases. But `wait_for_trace_bundle()` filters `ui_auto_debug` lines with `line.contains(&format!("session_id={session_id}"))`, which only matches unquoted IDs. It does handle code-block rows via `extract_session_id_from_line`, but not the primary `ui_auto_debug` row. 

**Impact:** If real traces use `session_id="abc"` format, debug/header runs can time out even though the trace is present.

**Fix:** In `wait_for_trace_bundle`, parse/extract `session_id` first, as the code-block path already does, then compare the parsed value. Add a regression test with a quoted `ui_auto_debug session_id="s1"` line.

**Status: FIXED** — `wait_for_trace_bundle` now uses `extract_session_id_from_line()` for ui_auto_debug lines, handling both quoted and unquoted session_id formats.

### 6. Stale log handling is documented but not actually used

`docs/troubleshooting.md` says the tool now uses `newest_trace_log_since()` for stale log avoidance, but that function is behind `#[cfg(test)]`; runtime paths call `newest_trace_log()` before launch and record that log path. 

**Impact:** The stale-log issue the docs claim is solved can still happen in real runs.

**Fix:** Remove `#[cfg(test)]`, call `newest_trace_log_since(launch_start_time)` after launching, and update offsets against the selected file. Keep a fallback only if no newer log is found.

**Status: FIXED** — Removed `#[cfg(test)]` from `newest_trace_log_since()`. Updated debug.rs, header_debug.rs, and prompt_debug.rs to capture `launch_start_time` before launch and check for newer logs after launch completes.

### 7. GPUI process output handling can deadlock and then writes empty logs

`run_process_with_optional_capture()` sets stdout/stderr to `Stdio::piped()`, but in the normal non-timeout path it calls `child.wait()` rather than `wait_with_output()` or concurrently draining the pipes. Afterward it writes empty stdout/stderr log files. The docs claim GPUI runs write stdout/stderr artifacts. 

**Impact:** If the GPUI example writes enough output to fill OS pipe buffers, the child can block and the harness can hang. Even successful runs produce misleading empty stdout/stderr artifacts.

**Fix:** Use `wait_with_output()` for normal runs, or spawn reader threads while polling for timeouts. Always write captured output to the artifact paths.

### 8. Error redaction is not safe enough

`format_safe_error()` iterates redacted env keys and replaces the key name with `KEY=[REDACTED]`, but it does not replace the actual secret value. For an error containing `OPENAI_API_KEY=sk-...`, this can still leave the secret in the message after the replacement. 

**Impact:** CLI error output can leak secrets if a command or error string includes env assignments.

**Fix:** Redact both `KEY=value` patterns and known secret values from the environment. Add tests for `OPENAI_API_KEY=sk-secret`, `--api-key sk-secret`, and token-looking values.

## Medium-priority issues

Scenario validation is inconsistent. `debug` rejects empty widths, but `header_debug` accepts empty widths at validation time and only fails during execution. `prompt_debug` validates successfully with empty `session_id` and empty prompt, even though `run_prompt_debug()` rejects both.

The artifact-kind story is not coherent. The artifacts crate defines stable kinds such as `summary_csv`, `trace_csv`, and `conversation_csv`, but adapters emit many uncatalogued kinds such as `gpui_csv`, `stdout_log`, `stderr_log`, `summary_tsv`, `top_strip`, and `header_focus`. Also, GPUI target-produced CSV/log/markdown artifacts are added with `add_artifact()`, so they default to `source: generated` even though they are imported from the target app.

The help/docs tests are too shallow. The “snapshot” tests mostly check that top-level help contains command names, not that subcommand flags, generated help, and docs agree. This explains why docs can drift while tests pass.

`format_failure_summary()` appears unused, and when it is used it computes the report path from `report.app_root` rather than the actual output directory. That is likely wrong.

The adapters include many direct X11/process calls, so core lifecycle cleanup is not the enforcement point. Cleanup is hand-coded per scenario, which raises the chance of inconsistent stop/restore behavior.

## Recommended next steps

1. **Stabilize CI first.** Gate Xvfb/openbox tests; run env-mutating tests serially or avoid global env mutation; add a CI job that actually installs X11/ImageMagick tools only for live/system tests.

2. **Fix report correctness.** Add `source` to the schema, mark failure reports as `error`, and add schema-validation tests over real generated report objects.

3. **Fix runtime correctness.** Update trace matching to parse session IDs, make `newest_trace_log_since()` production code, and capture subprocess stdout/stderr safely.

4. **Make the architecture honest.** Either wire adapters into `TargetAdapter`/lifecycle/driver abstractions, or rename those modules as experimental scaffolding. The current docs say “migration complete,” but the core abstractions are not the execution path.

5. **Tighten validation.** Validate required scenario fields before launch for every scenario, not only inside run functions.

The repo is promising, but I would not rely on it as a general-purpose automation harness until the schema/report bugs, CI gating, trace-log selection, and process-output handling are fixed.
